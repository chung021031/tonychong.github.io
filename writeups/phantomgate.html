PhantomGate v1.0

📅 May 2026 🏆 crackmes.one — AdminX 🔖 Reverse Engineering

Overview

PhantomGate is a 64-bit Windows crackme that demands a serial key in a four-group dash-separated format. What makes it interesting is that the validation logic is not a simple comparison — it is run inside a custom stack-based virtual machine, and the serial groups are encoded in a non-standard base-25 alphabet. Getting a valid key requires understanding both the encoding scheme and the VM computation, then using Z3 to satisfy the final constraint.

The serial format the program expects: 

XXXXX-XXXXX-XXXXX-XXXXX

A working serial:

4QJCG-P4R7Y-3VMY7-XRWHM

Step 1 — Anti-Debug Check

The very first thing main does before touching the serial input is run an anti-debug check. If a debugger is detected, the low bit of the first parsed group value gets flipped — silently corrupting the input so the VM equation can never be satisfied. The check itself does not crash or exit; it just poisons the data. Analyzing statically avoids this entirely.

Step 2 — Parsing the Serial

The input is validated to be longer than 0x16 characters, with dashes sitting at offsets 5, 11, and 17 — splitting the string into four 5-character groups. 

group0 - group1 - group2 - group3

Each group is decoded by a function (sub_1400014C0) using this custom alphabet: 

ACDEFGHJKLMNPQRTUVWXY3479

That is 25 characters, so each group is essentially a base-25 number. The accumulation formula is: 

value = value * 25 + index

where index is the character's position in the alphabet above. Four groups produce four 32-bit integers.

Step 3 — The Virtual Machine

The four decoded integers are loaded into VM registers 0–3. The program then constructs a bytecode sequence on the fly and hands it to a small stack-based interpreter. Tracing through the executed instructions and collapsing them into a single expression yields: 

target = 0x02D8EEC79A0331D6

v4 = (n0 * 2654435769) ^ n1
v5 = ror64(v4, 17) + n2
v6 = v5 ^ (n3 * 1818371886)
v7 = v6 ^ 2882400001

assert v7 == target   # all arithmetic mod 2^64

All four constants — the multipliers, the rotate amount, the XOR mask, and the target — are baked into the bytecode. The VM is single-purpose; it exists just to obscure what is essentially one equation.

Step 4 — Solving with Z3

Each group value is bounded by the base-25 range: 0 <= n <= 25^5 − 1. Plugging the equation and bounds into Z3 and asking for a satisfying model is straightforward: 

from z3 import BitVec, BitVecVal, Solver, ULE, ZeroExt, RotateRight, sat

ALPHABET = "ACDEFGHJKLMNPQRTUVWXY3479"
BASE = len(ALPHABET)
GROUP_LEN = 5
MAX_GROUP_VALUE = BASE**GROUP_LEN - 1

def encode_group(value: int) -> str:
    out = []
    for _ in range(GROUP_LEN):
        value, digit = divmod(value, BASE)
        out.append(ALPHABET[digit])
    return "".join(reversed(out))

parsed = [BitVec(f"p{i}", 32) for i in range(4)]
n = [ZeroExt(32, x) for x in parsed]

s = Solver()
for x in parsed:
    s.add(ULE(x, MAX_GROUP_VALUE))

expr = RotateRight((n[0] * BitVecVal(2654435769, 64)) ^ n[1], 17)
expr = expr + n[2]
expr = expr ^ (n[3] * BitVecVal(1818371886, 64))
expr = expr ^ BitVecVal(2882400001, 64)
s.add(expr == BitVecVal(0x02D8EEC79A0331D6, 64))

assert s.check() == sat
m = s.model()
groups = [m[x].as_long() for x in parsed]
serial = "-".join(encode_group(x) for x in groups)
print(serial)

One satisfying model produces the group values [8801280, 5040595, 8475523, 7652035], which encode back to: 

4QJCG-P4R7Y-3VMY7-XRWHM

Worth noting: the constraint is under-determined. Z3 finds one valid serial out of potentially many — other serials that satisfy the same equation are equally correct.

Key Takeaways

  • The anti-debug silently corrupts data rather than terminating — static analysis sidesteps it completely.
  • Custom alphabets and base-N encoding are a common way to make serials look opaque without heavy crypto.
  • Once a VM's bytecode is fully reduced to a closed-form expression, Z3 can solve it trivially with bit-vector constraints.

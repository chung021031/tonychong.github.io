Crackme Rev Easy

U Can't Pass

📅 May 2026 🏆 crackmes.one 🔖 Reverse Engineering

Overview

This was my first reverse engineering writeup, so I kept it simple. The binary is a tiny Linux program that always ends in the failure path. The point of the exercise was not to beat a hard crackme, but to practice reading disassembly and tracing the program flow.

Environment: WSL (Ubuntu)  |  Tools: GDB

Step 1 — Open It in GDB

I started by opening the binary in GDB and disassembling main. 

gdb main.out
disassemble main

Step 2 — Follow the Branches

The important part was not every instruction. What mattered was spotting that the program sets a local value to 10, compares it with 10, and then jumps over the success message every time. 

int main() {
    int a = 0;
    int b = 10;

    printf(greeting);       // always printed

    if (b == 10)            // ALWAYS true → jumps over success
        goto skip_success;

    printf(SUCCESS);        // dead code — never reached

skip_success:
    if (b != 10)            // ALWAYS false → never jumps
        goto skip_failure;

    printf(FAILURE);        // always printed

skip_failure:
    return a;               // return 0
}

Once rewritten like this, the answer is clear: there is no real check to beat. The binary is hardcoded to skip the success branch and print failure instead.

Step 3 — Final Result

The crackme does not accept input and does not contain a real success path. The value being compared never changes, so the output is fixed from the start.

Key Takeaways

  • Start by finding the main function and tracing the branch flow.
  • You do not need to understand every instruction to solve a simple crackme.
  • Rewriting the logic in plain C is often the fastest way to confirm what the program really does.

Tools Used

  • GDB (disassembly and annotation)
  • WSL / Ubuntu (execution environment)

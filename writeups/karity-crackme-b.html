Crackme Rev Hard

karity-crackme-B

📅 May 2026 🏆 crackmes.one — karity 🔖 Reverse Engineering

Overview

karity-crackme-B is a 64-bit Windows crackme written in C++. It asks for a 36-character input, runs it through a custom mixing function that closely resembles Galois Field GF(2²⁸) arithmetic, and compares the resulting 16-byte state against a hardcoded hash. Two subtle bugs in the implementation — a corrupted exponent table and an integer promotion issue — make naive symbolic solving hang indefinitely. The fix is to pre-compute dedicated look-up tables for every field constant and hand those to the QF_BV solver.

Flag: KARITY{secyh>pnnss(g6>* :e>@&>:\-rt}

Step 1 — Input Constraints

The first thing main enforces is a hard length limit: the input must be exactly 36 characters. Any other length exits immediately.

The next thing is a partial known-plaintext leak. A short loop reads indices 7, 8, and 9, XORs each byte with 0x59, and compares the result against a hardcoded string. Working backwards: 

input[7] ^ 0x59 == expected[0]   →   input[7:10] == "sec"

Combined with the visible flag format KARITY{...}, we know the flag starts with KARITY{sec and ends with } at position 35. That anchors 11 bytes before touching the heavy crypto.

Step 2 — The Mixing Function (GF(2⁸) Arithmetic)

The main validation function maintains a 16-byte state buffer, initialised to all zeros. For every input character, it loops 16 times and updates individual state bytes using a custom multiplication routine. The core of that routine — exponential and logarithmic look-up tables used to turn field multiplication into addition of logarithms — is textbook GF(2²⁸), the same field used in AES MixColumns.

The mixing step for each character at position v1 in the input: 

for each of 16 update rounds:
    state[idx] = GF_mul(state[idx], matrix_constant[k]) ^ input_char

where matrix_constant is the 16-byte little-endian encoding of two hardcoded 64-bit values: 

v41 = 0x026B703D14FC4C9A
v42 = 0x5FE21933C7A15581

Step 3 — Two Hidden Traps

Trap 1 — Corrupted Exponent Table

The exponent table in .rdata has 256 entries, but it contains repeating 13-byte chunks starting at offset 96. Because the program rebuilds the log table dynamically at startup by iterating over the exponent table, the duplicate entries overwrite earlier log values — producing a non-invertible, non-linear mapping that has nothing to do with a standard GF(2²⁸) field. Any solver that assumes clean field math will produce wrong results.

Trap 2 — C++ Integer Promotion

When computing the log sum LOG[a] + LOG[c] before taking it modulo 255, the program performs the addition in 32-bit registers rather than 8-bit. This means the intermediate sum can exceed 255 before the modulo, producing a different result than a pure 8-bit wrap. Modelling the multiplication using byte-width arithmetic silently breaks the equations.

Step 4 — Solver Strategy

A naive Z3 model with symbolic GF multiplications hits a combinatorial wall immediately — the non-linear field operations across 36 characters and 16 state bytes produce constraints too heavy for the general solver.

The fix: pre-compute a concrete 256-entry look-up table for each of the 16 matrix constants using the actual (corrupted) tables and the 32-bit addition semantics, then expose those to Z3 as static arrays. Every field multiply in the symbolic model becomes a simple array read — the solver only sees linear XOR operations and array selects, which QF_BV handles in under two seconds. 

# Build the real log table from the corrupted exp table
LOG_DATA = [0] * 256
for i in range(255):
    LOG_DATA[EXP_DATA[i]] = i   # later entries overwrite earlier ones

# Pre-compute one LUT per matrix constant
for k in range(16):
    c = const_matrix[k]
    lut = [0] * 256
    for a in range(256):
        if a == 0 or c == 0:
            lut[a] = 0
        else:
            # 32-bit addition before mod — mirrors the C++ promotion bug
            sum_log = (LOG_DATA[a] + LOG_DATA[c]) % 255
            lut[a] = EXP_DATA[sum_log]
    # Load lut into Z3 as a static array ...

With the 16 static LUT arrays in place, the state simulation becomes a chain of z3.Select calls and XOR operations, and the solver finds the flag trivially.

Key Takeaways

  • When a binary builds its own crypto tables at runtime, always verify them against a known reference — small corruptions silently destroy field properties.
  • C++ integer promotion in arithmetic operations can diverge from what you expect when modelling at a smaller bit width in a symbolic solver.
  • Pre-computing LUTs for heavy non-linear operations and injecting them as static Z3 arrays is a reliable way to make otherwise unmanageable constraint sets tractable.

Crackme Rev Hard

karity-crackme-B

📅 May 2026 🏆 crackmes.one — karity 🔖 Reverse Engineering

Overview

karity-crackme-B was the most technical of the group, but the solve path can still be kept simple. The program checks a 36-character input, mixes it into a state buffer, and compares the result against a target. The main task was finding enough fixed information to model the check and recover the flag.

Flag: KARITY{secyh>pnnss(g6>* :e>@&>:\-rt}

Step 1 — Lock Down the Known Input

The input has to be exactly 36 characters long, so that gave me the overall size right away.

There was also a small shortcut in the validation logic. A few characters could be worked out early, which revealed part of the prefix: 

input[7] ^ 0x59 == expected[0]   ->   input[7:10] == "sec"

Together with the visible format KARITY{...}, that gave a strong starting point before handling the bigger check.

Step 2 — Follow the State Update

The validator keeps a 16-byte state buffer and updates it repeatedly for each input character. I did not need to document every math detail in the writeup; the important part was confirming the repeated state update pattern across the whole input. 

for each of 16 update rounds:
    state[idx] = GF_mul(state[idx], matrix_constant[k]) ^ input_char

Step 3 — Match the Program's Real Behavior

Two things made the first solver attempts fail. First, one of the lookup tables in the binary was not clean, so modelling it like a normal textbook table gave the wrong result. Second, the arithmetic behavior in the program did not match a smaller 8-bit model.

Once I matched the program's real tables and real arithmetic behavior, the solver started making sense.

Step 4 — Use a Practical Solver

Instead of asking Z3 to handle the heaviest operations directly, I precomputed lookup tables first and then fed those simpler results into the solver. That made the model much lighter and let Z3 recover the correct flag.

Key Takeaways

  • Start with the fixed pieces: length, known prefix, and final comparison target.
  • If a direct solver model is too heavy, simplify the expensive parts first.
  • Matching the program's real behavior matters more than using the cleanest theory model.

Tools Used

  • IDA Pro (static analysis, field arithmetic identification)
  • Z3 (Python bindings — QF_BV solver with pre-computed LUTs)
